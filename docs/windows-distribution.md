# Windows x64 distribution

This document records the Phase 8 V1 packaging contract. It does not define an application auto-update or signing system.

## Stable identity

- Application/package name: `EVE Static Map Planner`
- Application version source: `appVersion` in `gradle.properties`
- Vendor: `Static Map Planner Project`
- Description: `Unofficial static map and route planning tool for EVE Online.`
- Main class: `dev.evestaticmapplanner.MainKt`
- Compatibility stdio launcher: `EVE Map MCP Bridge.exe`
- Stable Plugin stdio launcher: `eve-map-mcp.exe`
- Both MCP launcher main classes: `dev.evestaticmapplanner.mcp.MainKt`
- Upgrade UUID: `502B9850-A5B0-4922-BB20-AC7FEBA590DC`

The upgrade UUID identifies one installer product family. It must not change with the application version, Git commit, SDE build, build machine, or release artifact.

## V1 artifacts

- QA: self-contained application image from `:app:createDistributable`
- Distribution: unsigned Windows x64 MSI from `:app:packageMsi`
- Not produced: EXE installer, MSIX, Store package, ARM64, macOS, or Linux package

Native outputs are generated under `app/build/compose/binaries`. A release copy may be named `EVE-Static-Map-Planner-<version>-x64.msi`; the Git hash and SDE build do not belong in the filename.

## Build environment

- JDK: Eclipse Temurin 25.0.4+7 x64
- Gradle: wrapper version recorded in `gradle/wrapper/gradle-wrapper.properties`
- Kotlin and Compose: versions recorded in `gradle/libs.versions.toml`
- MSI tool: WiX Toolset 4.0.6 only
- WiX extension: `WixToolset.Util.wixext` 4.0.6 only

When the checkout path contains non-ASCII characters, JDK 25 can reject the
response file generated by Compose for `jlink`. Point Compose's native-only
working output at an absolute ASCII path without spaces:

```powershell
$env:WIX_PATH = Join-Path $env:USERPROFILE '.dotnet\tools'
.\gradlew.bat '-PnativeOutputDir=C:\Build\EVEStaticMapPlanner' :app:createDistributable
```

This property relocates generated `app`-module and native packaging output only.
Application data still uses `%LOCALAPPDATA%\EVE Static Map Planner`.

Install WiX on the build machine with:

```powershell
dotnet tool install --global wix --version 4.0.6
wix extension add -g WixToolset.Util.wixext/4.0.6
wix --version
wix extension list -g
```

The version checks must show WiX 4.0.6 and `WixToolset.Util.wixext` 4.0.6.
Do not substitute an unversioned/latest extension or WiX 3/5. The packaging
task also fails closed unless the Gradle runtime is JDK 25.0.4+7, because the
jpackage WiX authoring contract below was audited against that exact build.

WiX is a build-machine dependency only. The installed application contains its
own Temurin jlink runtime and does not require a system Java installation.
The app image and MSI must include the top-level notices and `legal/` bundle,
including the exact Temurin vendor notice, and must preserve the runtime's own
`legal/` tree and `release` metadata.

## Installation and data boundary

The MSI is a per-user install with Start Menu and desktop shortcuts for the GUI app. The main launcher does not open a console window. Both console MCP launchers are installed as product components but receive no shortcut or additional Installed Apps entry. All three launchers share one bundled runtime; the installer otherwise manages only application JARs, legal notice, icon, and immutable packaged resources.

For Plugin Gate A, WiX authors one per-user `Environment` table row that appends `[INSTALLDIR]` to the user's `PATH`. Windows Installer owns that entry: fresh install and repair do not duplicate it, explicit uninstall removes it, and a major upgrade removes the old product entry before installing the same logical entry for the new product. Other PATH entries are not replaced, reordered, or truncated. Already-running Codex processes must be fully restarted to inherit the updated environment.

Writable state remains outside the installation image:

```text
%LOCALAPPDATA%\EVE Static Map Planner\
├─ data\static.db
├─ data\user.db
├─ logs\
├─ updates\
├─ control\                 # ephemeral only while AI Control is active
└─ audit data beneath updates\
```

The package must not contain `active-instance.json`, `session.key`, `active.lock`, `settings.properties`, `static.db`, or `user.db`. Control discovery files are runtime session artifacts and are never migrated as installer data.

The installer contains no SDE database or SDE archive. First run without managed static data uses the Phase 7 Static Data Setup flow.

Uninstall removes the application and its locally stored application data. This includes managed `static.db`, `user.db` and Ansiblex connections, SDE updater cache/pending/backup state, and application logs. Reinstall therefore starts from `Static Data Setup`: Phase 7 downloads and rebuilds `static.db`, the application creates a new empty `user.db`, and Ansiblex CSV/JSON can be imported again. Manual Ansiblex entries, notes, or other data that was not exported cannot be recovered after uninstall.

Upgrade is different from explicit uninstall: an in-place MSI upgrade must retain the existing local data so the application can continue using its current static data, user database, and Ansiblex connections.

### Major-upgrade cleanup guard

JDK 25.0.4+7 jpackage generates one WiX `util:RemoveFolderEx` for the per-user
installation root. Its path is stored in
`RM_RF48431AECBD69377EA800D62616352F20`. Without a guard, the old product also
runs that recursive cleanup while Windows Installer removes it through
`RemoveExistingProducts`, deleting the co-located application data.

`app/src/main/jpackage/windows/main.wxs` is a jpackage Windows MSI template
override derived from the Temurin JDK 25.0.4+7 default `main.wxs`. Its only
installer-behavior change clears that dedicated RemoveFolderEx property after
`AppSearch` when `UPGRADINGPRODUCTCODE` is set. The recursive cleanup therefore
has no root during major-upgrade removal, while an explicit uninstall leaves the
property intact and deletes the complete application/data tree.

`RemoveExistingProducts` is sequenced after `InstallFinalize`. The replacement
product is therefore registered before Windows Installer removes the related
product, preserving shared component references. This matters when a Codex host
is actively using the installed MCP bridge during a same-version release-candidate
replacement: unchanged runtime and MCP files remain owned by the replacement and
are not queued for deletion on reboot.

Compose Multiplatform 1.10.0 does not expose a working public DSL hook for its
private jpackage resource directory. The `packageMsi` task therefore keeps
Compose's standard `createDistributable` application image, then invokes
jpackage's documented `--app-image` and `--resource-dir` mode with the same
identity, shortcut, per-user, version, and upgrade settings. There is no
unguarded MSI intermediate and no MSI binary post-processing.

Treat the template as a narrow compatibility asset, not as a general invitation
to customize WiX. Any JDK upgrade must diff and re-audit the upstream jpackage
`main.wxs`, the generated `bundle.wxf` property id, and this guard before an MSI
is published.

The exact upstream template is pinned to Adoptium `jdk25u` tag
`jdk-25.0.4+7`, path
`src/jdk.jpackage/windows/classes/jdk/jpackage/internal/resources/main.wxs`,
and template SHA-256
`932C805A5B28BF73844540BDF239F3CAAB943F01DBBAEE0160973A00B6B05120`.
Because the upstream file has no Classpath Exception designation, the adapted
template is treated separately under GPL-2.0-only. Its file-local modification
notice and `legal/openjdk-jpackage/OPENJDK-LICENSE.txt` must remain in source
and binary distributions. This does not impose that license on the project's
separate original source.

### Application-specific Component GUID namespace

JDK jpackage derives effective Component GUIDs independently of the stable MSI
UpgradeCode. Those GUIDs can collide with Components produced for an unrelated
application that packages identical files. To keep Windows Installer ownership
application-specific, `:app:packageMsi` uses this two-pass pipeline:

```text
jpackage probe MSI
  -> read effective Component GUIDs from the probe MSI
  -> transform the generated bundle.wxf
  -> UUIDv5 namespace every effective GUID
  -> build and verify the final MSI
```

The UUIDv5 namespace is the fixed UpgradeCode
`502B9850-A5B0-4922-BB20-AC7FEBA590DC`. The name contract is the literal prefix
`jpackage-component-guid-v1:` followed by the canonical effective probe GUID.
This keeps Components stable across versions of this application while a
different application namespace remains isolated. The 0.2.1 audited JDK
contract contains 257 generated Components: 256 generated explicit GUIDs and
one WiX auto-GUID RemoveFolderEx Component. One additional Planner-owned
Component registers the stable per-user PATH entry with fixed UUIDv5 GUID
`{44EBD78B-F3BB-5167-85E4-BD330EB5F4DF}`. The final MSI is accepted only when
all 257 generated effective GUIDs match the deterministic mapping and the PATH
Component retains that separate identity.

The probe MSI is diagnostic build output and is never published. Both the probe
MSI and transformed `bundle.wxf` remain below ignored build directories; the
generated override is not source-controlled. The final MSI is verified through
Windows Installer tables. No MSI binary is post-processed.

Any JDK upgrade must repeat the full drift audit: compare the upstream
`main.wxs`, generated `bundle.wxf`, Component count and identities, effective
probe GUIDs, RemoveFolderEx Component, final table mapping, cross-version
stability, and cross-application isolation before publishing an MSI.

### Legacy `.package` metadata cleanup

JDK 25.0.4+7 jpackage generates an `app\.package` metadata file. The Phase 8
pipeline removes only that generated `<File>` from the final payload and adds an
exact `RemoveFile` named `JpRemoveLegacyPackageMetadata` to the same always-active
Planner-owned Component in the `app` directory, with `Name=".package"` and
`On="install"`.

The final MSI File table must contain no `.package` row and its RemoveFile table
must contain exactly that cleanup. Wildcards, recursive application cleanup, and
targets beneath `data`, `updates`, or `logs` are forbidden. A JDK drift that
removes, duplicates, relocates, or changes ownership of the generated metadata
fails the transform rather than broadening the cleanup.

## Runtime modules

The explicit initial module set is:

```text
java.desktop
java.instrument
java.logging
java.net.http
java.sql
jdk.httpserver
jdk.unsupported
```

`java.instrument`, `java.net.http`, `java.sql`, and `jdk.unsupported` were reported
by `suggestModules`. `java.desktop` is required by Compose, and `java.logging`
is required by the rotating diagnostic log. `jdk.httpserver` serves the authenticated
loopback AI Control endpoint. The MCP launcher also uses `java.net.http`; its
production classpath is audited separately with `jdeps`. `suggestModules` is advisory. Final
correctness is established by `runDistributable` and installed-application
acceptance, including Compose/Skiko, SQLite native extraction, HTTP, ZIP, SDE
build, and database validation.

## Build metadata

Gradle generates `build-info.properties` under `app/build/generated`. It is packaged as a classpath resource and records application version, Git commit, JDK version/vendor, Kotlin, Compose, Gradle, target OS, and architecture. Git failures use `unknown` and do not fail ordinary builds. Build metadata must not contain a user name, developer path, or SDE build as the application version.

## Required acceptance

1. Clean build and all tests.
2. `suggestModules` review.
3. Create and inspect the application image.
4. Run the packaged image from an unrelated working directory without `JAVA_HOME`, `EVE_STATIC_DB`, or `EVE_USER_DB`.
5. Verify map, search, routes, Ansiblex, jump overlays, capital routing, SQLite, Static Data Manager, HTTP latest check, and an isolated first-run bootstrap.
6. Build the unsigned MSI and record size, SHA-256, Git commit, JDK, WiX, Compose, Kotlin, and Gradle versions.
7. Verify per-user install, UAC behavior, both GUI shortcuts, one Add/Remove Programs entry, all three launchers, and `eve-map-mcp.exe` resolution from a new terminal outside the install directory.
8. Verify uninstall removes the installer-managed application and the complete `%LOCALAPPDATA%\EVE Static Map Planner` tree, including isolated `static.db`, `user.db`, updater state, and logs. Reinstall must return to the Phase 7 first-run bootstrap.
9. Build 0.1.1 with `-PappVersion=0.1.1` and verify an in-place upgrade with the same upgrade UUID preserves the existing application data.
10. Complete final no-Java acceptance on a clean Windows x64 VM or another Windows x64 computer without Java.

## Phase 8 acceptance record

On 2026-08-20, the user reported completion of the final manual acceptance on
an independent Windows x64 machine with no JDK/JRE, no `JAVA_HOME`, and no
`java.exe` or `javaw.exe` on `PATH`. The copied 0.1.0 MSI matched SHA-256
`24CF3343299258A4541D847D16F11E9C0883224D872C1C2AF7291C500B31AD0B`.

The user-observed clean-machine results were: successful per-user installation
and both shortcuts; successful no-Java launch without a persistent console;
managed Phase 7 latest check, SDE download and automatic map entry; Current and
Latest SDE build `3473160`; successful map, system information, search,
Stargate route and manual Ansiblex smoke tests; successful close/relaunch without
another SDE download and with the Ansiblex entry preserved; and successful
normal uninstall with `%LOCALAPPDATA%\EVE Static Map Planner` removed.

This is a user-provided manual acceptance record, not an automated log. Combined
with the automated tests and isolated default-path install/upgrade/uninstall
lifecycle, the Phase 8 release acceptance passed.

## Signing and public release

Phase 8 V1 is unsigned. Unknown Publisher and SmartScreen warnings are expected for Internet-distributed artifacts. Do not create a self-signed certificate as a substitute for public trust, and never commit a PFX, P12, private key, or password.

V1 has no installer self-updater. Distribution scope is Windows x64 MSI only;
Microsoft Store/MSIX, macOS, and Linux packaging are outside Phase 8.

Before public distribution, complete a separate branding review covering the application name, icon, CCP notice, and unofficial/not-endorsed wording. `NOTICE.md` is a third-party notice and is not this project's source-code license.
